# docker-mediawiki
![CI](https://github.com/gesinn-it/docker-mediawiki/actions/workflows/main.yml/badge.svg)

Dockerized MediaWiki build on top of docker-mediawiki-base images in the style of the official MediaWiki Docker images with preinstalled Composer, MediaWiki and Xdebug (switched off by default, see below). Released on [dockerhub](https://hub.docker.com/r/gesinn/mediawiki). This image is intended to be used during development, testing and CI workflows.

- `$wgServer = http://localhost:8080`
- Wiki Admin: WikiSysop
- Password: wiki4everyone

(default) marks the PHP version used for tags without a PHP part (e.g. `1.43`). `gesinn/mediawiki` carries the same versions, but neither Xdebug, nor the tools, nor Node.js and npm: only `gesinn/mediawiki-ci` has Node.js and npm, taken from the official `node` image. ## Xdebug and code coverage

In `gesinn/mediawiki-ci`, Xdebug is loaded but switched off (`XDEBUG_MODE=off`), so PHPUnit runs at full speed. Enable it per run with the environment variable, which takes precedence over the ini file:

```yaml
# docker compose override
services:
  wiki:
    environment:
      XDEBUG_MODE: coverage   # or debug, develop, ...
```

[PCOV](https://github.com/krakjoe/pcov) is installed in the image as well, but not enabled. It collects line coverage several times faster than Xdebug. To use it:

```sh
docker-php-ext-enable pcov   # as root
echo 'pcov.directory=/var/www/html/extensions/MyExtension' >> /usr/local/etc/php/conf.d/docker-php-ext-pcov.ini
```

Without `pcov.directory`, PCOV looks for `src`, `lib` or `app` below the working directory and finds nothing when PHPUnit runs from the MediaWiki root.

The versions are also available as image labels and as annotations on the multi-arch index, so they can be read without pulling the image:

```
docker buildx imagetools inspect gesinn/mediawiki-ci:1.43-php8.2 --format '{{json .Manifest.Annotations}}'
```

| Label | Content |
|---|---|
| `org.opencontainers.image.base.name`, `org.opencontainers.image.base.digest` | `gesinn/mediawiki-base` image the build used, and its digest |
| `org.opencontainers.image.version`, `it.gesinn.mediawiki.version` | MediaWiki version |
| `it.gesinn.php.version` | effective PHP version, e.g. `8.2.34` |
| `it.gesinn.composer.version` | Composer version |

| `it.gesinn.nodejs.version`, `it.gesinn.npm.version` | version of the `node` and `npm` binaries (`mediawiki-ci` only, from the official `node` image) |
| `it.gesinn.tools.version` | version of [docker-mediawiki-tools](https://github.com/gesinn-it-pub/docker-mediawiki-tools) (`mediawiki-ci` only) |

## Build matrix

`matrix.json` is the list of the combinations that are built, one entry per MediaWiki and PHP version, with the PHP version that the tags without a PHP part (e.g. `1.43`) point to:

```json
{"mediawiki_version": "1.43", "php_version": "8.3", "php_default": "8.3"}
```

Every entry is built for both image types, `mediawiki` and `mediawiki-ci`. A push to `main` builds all entries. A manual run (`workflow_dispatch`) can be restricted to one MediaWiki and / or PHP version; the combination has to be in `matrix.json`, otherwise the run stops in the `plan` job. [docker-mediawiki-base](https://github.com/gesinn-it/docker-mediawiki-base) triggers this workflow for the combinations of its own `matrix.json` that have `"downstream": true`: an entry that is added or removed there has to be added or removed here as well.

## Security advisories

Composer does not block the image build on security advisories (`policy.advisories.block` is `false`): a finding in a dev dependency, which the `mediawiki` image does not even install, must not stop a build. Instead the build runs an audit gate (`audit-gate.php`) after `composer update`:

| Image | Gate | Effect |
|---|---|---|
| `mediawiki` | `strict`, installed (non-dev) packages | high or critical advisories fail the build, everything else is reported as a warning |
| `mediawiki-ci` | `warn`, including the dev tools | all advisories are reported, none fails the build |

Advisories without a severity are treated as warnings. The warnings are part of the build log.

A high or critical advisory that cannot be fixed (e.g. because MediaWiki pins the vulnerable version) is accepted in `audit-triage.json`, with a reason and a date to review it again:

```json
{
	"PKSA-xxxx-xxxx-xxxx": { "reason": "why this is acceptable for now", "review": "2026-12-01" }
}
```

Accepted advisories are still printed. An expired review date is printed as a warning, it never fails a build.
